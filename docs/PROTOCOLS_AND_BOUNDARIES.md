# Protocols and boundaries

| Protocol | Status | Boundary |
| --- | --- | --- |
| `state.v1` | frozen | Read-only normalized current facts for a decision; built on demand, not by a high-frequency snapshot task. |
| `vision.v1` | implemented | One structured image observation per fixed plant zone; appearance only, never a diagnosis, strategy, or device control. Not enabled: no consumer exists, and no camera or provider request runs unless explicitly configured and separately approved. |
| `strategy.v1` | implemented | Structured proposal bound to one `state.v1` snapshot by `device_code`, that snapshot's `observed_at`, and a `state_sha256` fingerprint the local service computes from it; `state_generated_at` is traceability metadata, not a binding condition, and every timestamp is carried in one RFC 3339 UTC notation the service normalizes to. Only `water(pump_seconds)`, `wait(seconds)`, `observe`, and `stop` actions are allowed, each within a protocol ceiling and within a cumulative ceiling for the whole strategy. It never grants execution or device-control authority, and only a declared projection of `state.v1` is ever sent to a provider. The soil3 runtime consumes it through Validator → Gate → dry-run Runner; the shipped provider configuration remains disabled and has not been exercised against a live provider. |
| `gate.v1` | implemented | Read-only admission decision bound to one validated `strategy.v1` and `state.v1`; it records a local exploration-budget reservation but never grants device-control authority. |
| `gate.v2` | implemented | Read-only admission decision with the same safety and budget boundary as `gate.v1`, plus a Gate-local canonical `strategy_sha256` for every formally validated complete `strategy.v1`, including a final Gate deny; the field is `null` only when formal validation fails. It grants no device-control authority. `gate.v1` remains compatible for its existing consumers, but a later Phase3 Bridge consumer must reject it rather than infer a content binding from `strategy_id`. |
| `episode.v1` | implemented | Structured care-experience record with an `open → closed` lifecycle (`create`, `update`, `read`, `close`): one episode embeds one real `state.v1` snapshot plus a store-computed `state_sha256` under the strategy.v1 binding encoding, and links the caller-supplied strategy, gate result, executed actions, feedback, and outcome. Decision sections are set-once, fact sections append-only, and a closed record is immutable. Structured reasons, confidence, and outcome evaluations are preserved as supplied; sections nobody supplied are listed in `missing_facts` at close instead of being fabricated, and the model's hidden thought process is never stored — reasoning-shaped payload keys are refused. It grants no execution and touches no device, Phase3, or historical data. Gate and Feedback are implemented by their own modules, while Episode preserves their caller-supplied records with envelope checks. The soil3 runtime creates and updates an open Episode, then Feedback finalization writes the one aggregate Outcome and closes it; no path reopens or modifies a closed Episode. |
| `feedback.v1` | implemented | Factual post-action observations for one `episode.v1` care experience at four windows (30min, 2-3h, 6-12h, 24h): caller-supplied soil and visual facts plus the independent assessments recovery, sustained dryness, sustained wetness, rewater need, and data quality. Assessments nobody supplied stay `"unknown"` and observations nobody supplied stay `null` and are listed in `missing_observations`; contradictory data is preserved and flagged with machine codes, never reconciled, repaired, or deleted; ids, timestamps, contradictions, and the missing list are store-computed, and reasoning-shaped keys are refused anywhere in a payload. Aggregating an episode's records into an outcome payload keeps the evaluations independent with per-value window provenance — no unified reward is computed. Incremental attach appends facts while the runtime Episode remains open; explicit finalization sets the Outcome once and closes it through `EpisodeStore`. It schedules no collection (visual collection timing is Issue #30), grants no execution, and never reopens or changes a closed Episode. Observation scheduling remains not enabled. |
| `trace.v1` | implemented | Local analysis-only association record for one Shadow decision attempt. It stores only typed references to already-produced records and explicitly sourced model metrics; it never copies a business object, invents a missing fact, calculates reward, makes a decision, or grants execution. Decision-stage associations are set-once, Feedback references are append-only, and the Outcome reference is set once from `null`. Its execution statement is permanently `phase3_called=false` and `physical_actions_performed=false`; Trace is not an input to Phase3, Gate, Runner, MQTT, ActuatorLayer, or a pump path. |
| `experience_retrieval.v1` | implemented | Read-only ranking over closed `episode.v1` files. Successful and failed cases remain separate; each match exposes feature values, distances, weights, similarity and evidence coverage. Missing evidence lowers coverage, while absent, unknown, or conflicting Outcome labels are never guessed. It has no strategy, Feedback, Bridge, Phase3, actuator, or database-write authority. |
| `replay_sample.v1` | frozen | Read-only reconstruction of `state.v1` from facts timestamped at or before an inclusive historical cutoff T; future facts are excluded and data-quality limitations remain explicit. |

“Planned” means no public contract is implemented yet. Do not write consumers that assume a planned protocol already exists. Read this document for State or shared-protocol work; it is not mandatory background for every ordinary task.

“Implemented” means the contract has an implementation covered by automated tests, but is not yet frozen: compatibility iteration may continue inside later implementation Issues. A consumer that needs a stable contract must wait for “frozen”. Whether a protocol has been exercised against real devices or a live provider, and whether it is enabled at runtime, are stated per protocol in the Boundary column and in its implementation Issues; neither is implied by this status.

Frozen protocols cannot be changed inside one implementation Issue. Any required change must be an explicit protocol-change proposal, include version/compatibility handling, and identify all producers and consumers before implementation.
