# 植物智能体云端大模型接入与边云协同计划书（V3）

## 一、目标

当前植物系统已经能够自动浇水，但浇水方式仍主要依赖人工预设。

本阶段目标是：

> 让云端大模型结合实时植物状态、环境变化、视觉状态和历史反馈，动态生成新的浇水策略，并在较宽松但有底线的 Safety Gate 下进行真实试探；同时完整记录运行过程，为后续 Qwen3.5-2B 小模型训练提供高质量真实数据。

时间安排：

- 前 8 个工作日：完成当前阶段全部核心功能
- 第 8 个工作日结束后：冻结 V1
- 剩余时间：稳定运行、修 Bug、持续产生真实 Episode 数据

开发方式：

- Codex：主要代码开发、测试、联调、代码审查
- GitHub：版本管理、Issue 任务管理、提交记录、回滚依据
- 每个工作日建立对应 GitHub Issue
- 每完成一个明确功能点即提交 Git
- 每日结束前更新 Issue 验收结果和遗留问题

# 三、云端大模型输入

由 `State Builder` 统一整理，不让模型直接读取原始数据库。

第一版输入包括：

- 土壤湿度
- 环境温度
- 空气湿度
- 光照
- 最近 1h / 3h / 6h 变化趋势
- 上次浇水时间
- 上次浇水量
- 距离上次浇水时间
- 最近几次 Episode 结果
- 当前视觉状态
- 当前安全状态

预留但暂不实现：

```json
{
  "pot_weight_g": null,
  "bottom_water_level": null,
  "runoff_detected": null,
  "extensions": {}
}
```

# 五、策略生成

大模型不从预设策略 A / B / C 中选择，而只使用基础动作：

```text
water(x)
wait(t)
observe()
stop()
```

例如：

```text
water(20mL)
↓
wait(20min)
↓
observe()
↓
恢复明显 → stop()
恢复不足 → 再次分析
```

目标是让大模型动态组合策略，而不是继续执行人工固定浇水方式。

# 七、宽松 Safety Gate

原则：

> Safety Gate 只阻止明显危险动作，不替大模型决定什么才是“正确策略”。

三种结果：

```text
allow
allow_with_warning
deny
```

硬拒绝只保留少量底线：

- 传感器明显故障
- 执行器异常
- 单次水量达到明显危险级别
- 极短时间累计浇水达到危险水平
- 已存在明显异常仍持续执行

其他偏激进动作优先使用 warning，而不是直接拒绝。

同时使用“探索预算”：

```text
本轮总探索量不得突破安全上限
```

至于如何分配：

```text
30mL一次
20 + 10
15 + 10 + 5
```

由大模型自行决定。

# 八、Episode 与真实反馈

每次真实浇水建立一个 Episode。

记录：

```text
State
+
Cloud Strategy
+
Safety Gate
+
实际 Action
+
真实 Feedback
```

反馈周期：

- 浇水前 2～6h
- 约 30min
- 2～3h
- 6～12h
- 24h

反馈内容：

- 湿度恢复幅度
- 恢复速度
- 是否维持稳定
- 是否短时间再次补水
- 是否持续高湿
- 视觉状态是否改善
- 是否出现异常
- 数据质量

第一版不要求统一 Reward 总分，先保留独立评价：

```json
{
  "recovery": "good",
  "persistence": "good",
  "underwatering": false,
  "overwatering": false,
  "rewater_needed": false,
  "visual_recovery": "good",
  "data_quality": "good"
}
```

成功和失败 Episode 都必须保存。

# 十、GitHub + Codex 开发方式

每天围绕一个主 Issue 工作。

建议流程：

```text
GitHub Issue
    ↓
Codex 阅读 Issue + 当前代码
    ↓
先检查现有实现
    ↓
制定最小修改方案
    ↓
编码
    ↓
测试
    ↓
真实/模拟验证
    ↓
提交 Git
    ↓
更新 Issue 验收结果
```

每个 Issue 建议只包含：

1. 当天目标
2. 要实现的核心功能
3. 必须保持的边界
4. 验收标准
5. 最终结果记录

避免在 Issue 中写过长的设计文档。

# 十一、Git 提交原则

建议按可回滚功能点提交，而不是一天只提交一次大改动。

例如：

```text
feat: add unified plant state schema
feat: add visual state analyzer adapter
feat: add cloud strategy agent
feat: add multi-step strategy executor
feat: add exploratory safety gate
feat: add watering episode recorder
feat: add episode feedback retrieval
fix: handle invalid cloud strategy output
```

每天结束前保证：

- 工作区清晰
- 测试通过
- 当前可运行状态已提交
- Issue 中记录当前状态
- 不把未完成的大量实验代码混进稳定分支

# 十五、最终目标

最终系统不是：

```text
固定规则控制
```

也不是：

```text
所有情况都让云端大模型控制
```

更不是：

```text
最后全部交给小模型
```

而是：

```text
云端大模型负责探索和复杂情况
        ↓
真实植物反馈验证
        ↓
形成高质量经验
        ↓
训练本地小模型
        ↓
小模型接管自己能够可靠处理的场景
        ↓
不能可靠处理的继续交给云端
```

Safety Gate 始终只负责守住安全底线。

最终形成能够持续适应环境变化和植物个体差异的边云大小模型协同植物智能体。
